## 1. 项目概述

### 1.1 背景与问题

在大型项目开发中，关键模块的实现选择（如数据结构、算法、缓存策略等）往往在开发初期无法确定最优方案。团队通常采取"先跑通，后优化"的策略，但当后期需要替换核心实现时，会面临：

- 代码中大量直接依赖具体实现类，替换需要大规模修改
- 缺乏对"哪些组件未定"的统一管理，状态不透明
- 替换后无法系统化验证功能一致性和性能差异
- 固化决策缺乏数据支撑，依赖个人判断

### 1.2 核心理念："未干的胶水"

将关键位置视为可替换组件，通过未固化的胶水层连接调用方与实现方。胶水未干时，实现可以自由更换；确认最优方案后，显式执行"固化"操作，锁定实现。整个过程可测试、可追踪、可回滚。

### 1.3 项目目标

研发一套完整的可替换组件生命周期管理平台，具备：

- 组件注册与状态管理
- 可视化操作面板
- 测试与性能对比
- 固化流程与防误操作机制
- 可选 AI 辅助迁移模块

## 2. 核心概念定义

| 概念 | 说明 |
|---|---|
| 可替换组件 | 项目中可以存在多种实现的关键模块（如索引结构、缓存策略、序列化器） |
| 胶水层 | 连接调用方与具体实现的抽象边界，包含接口定义、适配逻辑和状态管理 |
| 未固化状态（experimental） | 组件处于实验阶段，实现可自由切换，胶水保持可塑 |
| 候选状态（candidate） | 正在对多个实现进行对比测试 |
| 固化状态（sealed） | 已确认最优实现，胶水锁定，普通操作无法修改 |
| 解固化（unseal） | 重新开放组件的实验状态，允许再次切换 |
| 胶水开销 | 胶水层引入的运行时性能成本（代理、适配、类型转换等） |

## 3. 系统架构

### 3.1 核心模块

```
┌─────────────────────────────────────────────────────────┐
│                    可视化面板（Web UI）                   │
├─────────────────────────────────────────────────────────┤
│  组件注册中心    │   状态管理器    │   测试/基准引擎       │
├─────────────────────────────────────────────────────────┤
│  依赖分析器      │   固化控制器    │   历史归档系统         │
├─────────────────────────────────────────────────────────┤
│  AI 辅助模块（可插拔，默认关闭）                           │
│  ├── 代码迁移助手                                         │
│  ├── 影响分析器                                           │
│  └── 优化建议生成器                                       │
├─────────────────────────────────────────────────────────┤
│  配置存储（YAML/Lockfile）    │   代码仓库集成（Git/CI）   │
└─────────────────────────────────────────────────────────┘
```

### 3.2 组件生命周期

```
[创建] → [实验(experimental)] → [候选(candidate)] → [固化(sealed)]
                 ↑                    │                    │
                 │                    │                    │
                 └────── 解固化(unseal)←────────────────────┘
                              │
                              ↓
                        [归档(archived)]
```

### 3.3 胶水层设计

胶水层支持两种形态：

**A. 固定型胶水：接口固定，仅实现可替换**

```
调用方 → 稳定接口 → 具体实现（可切换）
```

**B. 可塑型胶水：接口本身可变化，胶水自动适配**

```
调用方 → 动态代理/适配层 → 具体实现
              ↑
         映射规则配置
    （方法映射、参数转换、返回值解包）
```

## 4. 核心功能需求

### 4.1 组件注册与发现

```yaml
# swappable.yaml
components:
  index:
    interface: Index
    implementations:
      - name: bplus
        class: BPlusTreeIndex
      - name: rbtree
        class: RedBlackTreeIndex
    status: experimental
    selected: bplus
```

- 支持注解/配置文件/编程式三种注册方式
- 自动扫描项目中的 @Swappable 标记
- 生成组件注册表供运行时查询

### 4.2 状态管理

| 操作 | 前置条件 | 权限要求 |
|---|---|---|
| 切换实现 | 组件未固化 | 管理员 |
| 固化 | 测试通过 + 人工确认 | 管理员 |
| 解固化 | 组件已固化，需额外确认 | 管理员 |
| 归档 | 组件已固化 | 管理员 |

防误固化机制：

- 测试命令无写权限，仅输出报告
- 固化需独立命令且二次确认
- CI 中禁止自动执行固化
- 所有状态变更记录到 swappable.lock 并提交版本控制

### 4.3 测试与基准

功能一致性测试：

- 同一组测试用例对多个实现分别运行
- 结果自动对比，差异高亮

性能基准测试：

- 对比吞吐量、延迟、内存占用
- 支持自定义负载模式

胶水开销测试：

- 实验模式（带胶水）性能
- 固化模拟（去胶水）性能
- 计算胶水开销百分比

### 4.4 依赖违规检测

- 静态分析扫描代码，检测是否直接依赖未固化组件的具体实现类
- 违规位置精确定位到文件和行号
- 与 CI 集成，违规时阻断合并

### 4.5 风险等级评估

基于依赖广度自动计算：

| 风险等级 | 判定标准 | 操作限制 |
|---|---|---|
| 低 | 依赖模块 < 5，无直接实现类引用 | 可自由切换 |
| 中 | 依赖模块 5-20，或少量直接引用 | 切换需测试报告 |
| 高 | 依赖模块 > 20，或大量直接引用 | 强制渐进式迁移 |
| 核心 | 被全系统依赖，无法隔离 | 标记为永久固化 |

## 6. AI 辅助模块（可插拔设计）

### 6.1 设计原则

- 核心工具不依赖 AI：AI 功能默认关闭，核心管理功能完全独立可用
- AI 作为可替换组件：AI 模块本身遵循工具的核心理念，通过接口定义，可插拔
- 人工审查始终必要：AI 生成的修改必须经过人工确认

### 6.2 AI 模块架构

```java
public interface MigrationAssistant {
    List<CodeChange> analyzeImpact(AffectedCodeContext context);
    List<CodeChange> generateMigration(AffectedCodeContext context,
                                        OldInterface oldInterface,
                                        NewInterface newInterface);
    List<OptimizationSuggestion> suggestOptimizations(CodeRegion region);
}

// 无 AI 实现
public class RuleEngineAssistant implements MigrationAssistant { ... }

// OpenAI 实现
public class OpenAIAssistant implements MigrationAssistant { ... }

// 本地模型实现
public class LocalModelAssistant implements MigrationAssistant { ... }
```

### 6.3 AI 迁移工作流

```
1. 用户发起组件切换
2. 工具扫描受影响代码 → 生成依赖图谱
3. [可选] 调用 AI 分析影响范围
4. [可选] AI 生成适配代码建议（diff 形式展示）
5. 人工审查每个修改建议（接受/拒绝/调整）
6. 工具应用确认后的修改
7. 运行测试套件
8. [可选] AI 输出额外优化建议（不自动应用）
9. 用户决定是否采纳优化建议
```

### 6.4 API Key 管理

- 加密存储，仅管理员可见
- 支持多提供商配置（OpenAI/Azure/本地模型）
- 调用失败时自动降级到规则引擎模式
- 支持按组件、按模块配置不同的 AI 模型

## 7. 核心技术决策

### 7.1 胶水层实现技术选型

| 方案 | 适用场景 | 优点 | 缺点 |
|---|---|---|---|
| 固定接口 + DI 容器 | 接口稳定，仅实现变化 | 简单，性能好 | 接口变化时需改调用方 |
| 动态代理 | 接口可能变化 | 灵活，调用方无需修改 | 性能开销较大 |
| 编译期代码生成 | 两端形状已知 | 性能接近直接调用 | 构建复杂度高 |
| 元数据驱动适配 | 接口映射较复杂 | 映射规则可配置 | 需要维护映射配置 |

推荐策略：默认使用固定接口 + DI，当接口变化时启用动态代理/代码生成作为过渡，固化时移除动态层。

### 7.2 固化优化策略

固化操作不仅仅是"锁定状态"，还包含性能优化：

- 移除动态代理层
- 适配逻辑编译期内联
- 消除不必要的类型转换
- 启用语言级优化（如 JIT 内联）

固化后的代码理论上等价于直接调用实现类，胶水开销趋近于零。

## 8. 市场定位与差异化

### 8.1 现有工具覆盖情况

| 能力 | 现有工具 | 差距 |
|---|---|---|
| 接口替换 | Spring/Guice/Dagger | 无状态管理，无固化概念 |
| 运行时切换 | Feature Flag 平台 | 面向业务功能，非代码内部组件 |
| 依赖检测 | ArchUnit/JDepend | 无生命周期管理，无面板 |
| 基准测试 | JMH | 需手工组织，无决策支持 |
| 灰度验证 | Istio/Linkerd | 面向服务间流量，过于重型 |

### 8.2 本项目差异化

- 首创"未固化/固化"生命周期管理，将架构决策过程显式化
- 胶水开销可视化，量化保留灵活性的成本
- AI 辅助迁移，降低核心组件替换的修改成本
- 一体化平台，覆盖从实验到固化的完整流程

## 9. 现实限制与应对

| 限制 | 说明 | 应对策略 |
|---|---|---|
| 接口设计难度 | 接口太窄限制实现，太宽增加胶水复杂度 | 提供接口设计指南和模板 |
| 无法完全去除胶水 | 某些语义映射固化后仍需保留 | 编译期生成减少运行时开销 |
| 已有项目接入成本 | 历史代码无接口边界 | 提供渐进式接入工具，自动识别可组件化位置 |
| 性能敏感性 | 胶水层对高性能组件可能有明显影响 | 胶水开销测试帮助判断是否值得保留灵活性 |
| 团队接受度 | 部分团队可能认为过度设计 | 风险等级评估帮助聚焦关键组件 |

## 11. 总结

「胶水」项目致力于解决软件架构中关键实现决策的延迟与安全固化问题。通过将"未干胶水"概念工程化，提供从实验、对比、决策到固化的完整工具链。核心设计原则是：在不牺牲灵活性的前提下，让团队清楚地知道灵活性的代价，并在合适的时机安全地消除它。

AI 辅助模块作为可选增强，帮助团队在核心组件更换时降低下游修改成本，但绝不成为核心功能的依赖项。整个系统遵循"胶水"自身的哲学——按需粘合，用完可移除，始终保持可塑性与可控性。
