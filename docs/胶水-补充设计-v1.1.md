## 0. 为什么是这两项

v1.0 是一份合格的**产品**设计，但在**工程**层面有两个前提没落地：

| 缺口 | 后果 |
|---|---|
| 未声明目标技术栈 | 所有实现路径（代码生成、代理、静态分析、基准）都无法选型，路线图无法估算 |
| 未考虑数据兼容性 | 在有持久化/跨进程格式的场景下，切换实现不是换类而是数据迁移——工具的生命周期模型直接失效 |

这两项不是"补充功能"，是**会决定项目成败的前提**。

# 一、深挖（二）：目标技术栈

> **2026-09-04 修正**：初版把「目标语言」与「工具语言」混为一谈，见 §1.0。

## 1.0 【重要修正】「技术栈」其实是三个独立问题

这一定位暴露了初版的疏漏。技术栈是三个问题，答案不必相同：

| # | 问题 | 指什么 |
|---|---|---|
| **A** | **目标语言** | 被管理的项目（组件与实现）用什么语言写 |
| **B** | **工具语言** | 「胶水」这个工具本身用什么语言写 |
| **C** | **分发形态** | 用户怎么装、怎么在 CI 里跑 |

v1.0 中两类证据此前被合并判定为「Java」，不严谨：

- 属于 **A** 的证据：Spring / Guice / Dagger（§7.1）、JMH（§8.1）、JIT 内联（§7.2）、`@Swappable`（§4.1）
- 属于 **B** 的证据：`public interface MigrationAssistant`（§6.2 —— 这是**工具自身**的代码）

## 1.1 问题 A：目标语言 —— 必须钉死在 JVM，这是产品定位问题

**决定性论据：「胶水开销」这个核心卖点只在部分语言上成立。**

| 目标语言 | 虚分派开销真实存在？ | 固化收益 | 「胶水」价值 |
|---|---|---|---|
| **Java / Kotlin / C#** | 是（megamorphic 时显著） | 大：剪枝 → 单态 → 内联 | **高** |
| **Go** | 是（itab 动态分派） | 中：需代码生成或类型参数单态化 | 中高 |
| **C++** | 部分（虚表） | 中，但运行时热切换困难 | 中低 |
| **Rust** | 部分（trait object） | 低 —— 泛型单态化已是语言级答案 | **低** |
| **Python / TS / JS** | **几乎不存在**（本来就是全动态分派） | 无 | **极低** |

- **动态语言里「接口」不产生额外开销，「胶水开销量化」这个卖点直接消失。**
- **Rust 里 generics 已经把「编译期固化」做成了语言特性**，工具没有增量价值。

这不是实现细节，是**产品定位**：做成「多语言通用工具」，等于在一半的目标语言上卖一个不存在的价值。

**建议**：v1 目标语言钉死 **Java 11+（建议 17+）**；Go / C# 列入 Phase 6+，进入前必须重跑 §1.6 的开销验证；Python / TS / JS / Rust **明确不做**（卖点不成立，不是「以后再说」）。

### 判定依据（来自 v1.0 文本，问题 A）

| 证据 | 出处 | 指向 |
|---|---|---|
| `public interface MigrationAssistant` / `implements` | §6.2 代码块 | Java 语法 |
| Spring / Guice / Dagger | §7.1、§8.1 | JVM DI 生态（三者均为 JVM） |
| JMH | §8.1 | Java Microbenchmark Harness，**JVM 专有** |
| JIT 内联 | §7.2 | JVM 运行时概念 |
| `@Swappable` 注解扫描 | §4.1 | Java 注解语法（非 Go struct tag、非 TS 装饰器写法） |
| 编译期代码生成 | §7.1 | JVM 对应 APT / 字节码织入 |

### 结论（问题 A）

> **判定：目标语言为 JVM / Java，v1 不含 Kotlin / Scala。**

理由：Kotlin 的扩展函数、默认参数、`object` 单例会干扰接口适配与静态分析；Scala 的隐式转换会让「依赖违规检测」产生大量误判。v1 不支持，标记为 Phase 6+。

⚠️ **待确认**：A 与 B 需分别拍板。若目标语言不是 JVM，§1.4 起的内容需整体重做。

## 1.2 问题 B：工具自身语言 —— 不必须是 Java，且 Java 有硬伤

作为「工具链包」，工具自身用 Java 的短板很具体：

| 维度 | Java 写工具 | Go / Rust 写工具 |
|---|---|---|
| **分发** | 目标机需装 JDK；CI 镜像、非 Java 团队机器上常缺 | **单二进制，零依赖** |
| CI 集成 | 需先配置 JDK | 下载即用 |
| 启动速度 | 慢（JIT 预热），CLI 体感差 | 快 |
| 静态分析 | 分析 Java 很强（Spoon / JavaParser / ArchUnit） | 任意语言皆可，用 **tree-sitter** |
| 不可替代项 | **APT 注解处理器必须是 Java**（javac 的一部分） | 无 |

硬约束：只要目标语言是 Java，**APT 代码生成与构建期剪枝必然属于 JVM 侧**，无法绕开。

### 工具语言的选型：为什么不是 C

选型应按**这个工具的实际工作负载**评判，而不是泛泛的语言优劣。它的 90% 工作量是：

> 遍历目录、读写大量小文件、字符串处理（切行 / 缩进 / dedent / diff / hash）、维护 Map-Set-List（区域表、候选表、元数据）、解析 key=value 配置、起一个 HTTP 服务做面板、调用子进程（Gradle / Maven / JMH）。

| 语言 | 分发 | 上述负载的开发成本 | tree-sitter | 结论 |
|---|---|---|---|---|
| **Go** | 单二进制，`GOOS/GOARCH` 一行交叉编译 | **低**：标准库自带 HTTP / JSON / regexp / 测试框架 | 有社区 binding | **推荐** |
| **Rust** | 单二进制，最优 | 中：serde / clap / axum 都很成熟，但开发速度慢 30–50% | **binding 最成熟** | 次选 |
| **TS（Deno / Bun 编译）** | 需 Deno/Bun 或打包 | 低 | **官方 binding 最好** | 若团队是前端出身可选 |
| **C** | 单二进制 | **高**：无 hash map、无字符串类型、无 JSON、无 HTTP server、无跨平台路径处理，全部自造或引第三方 | 原生（tree-sitter 本身是 C） | **不推荐** |

**C 的问题不是能力，是投入产出。** 它唯一的真实优势是能直接调用 tree-sitter 的 C 代码、无 FFI 开销。但这个工具的性能瓶颈是**磁盘 IO 与子进程调用**，不是 CPU——用 3–5 倍的开发成本去换一个用不上的性能优势，是净亏损。

（如果真需要 C 级互操作又想要安全与效率，**Zig** 比 C 更合适：可直接 `@cImport` tree-sitter，交叉编译也是强项。但生态不成熟，不适合需要长期维护的工具链。）

**何时才值得换掉 Java**：当且仅当分发问题真正成为阻塞——即需要把工具发给没有 JDK 的机器或 CI 镜像时。在此之前不要过早重写。

## 1.3 问题 C：分发形态 —— 推荐「引擎与语言前端分离」

```text
┌────────────────────────────────────────────────┐
│  核心引擎（Go，单二进制）                        │
│  CLI / 状态机 / lock / Web 面板 / CI / 静态分析   │
└───────────────────┬────────────────────────────┘
                    │  JSON schema（稳定契约）
        ┌───────────┼───────────┐
        ↓           ↓           ↓
   ┌─────────┐ ┌─────────┐ ┌─────────┐
   │Java 前端│ │ Go 前端  │ │ C# 前端  │
   │(Gradle) │ │ (P6+)   │ │ (P6+)   │
   └─────────┘ └─────────┘ └─────────┘
```

- **核心引擎（不绑定 JVM，建议 Go）**：CLI、状态机、`swappable.lock` 读写、Web 面板（内嵌静态资源）、CI 集成、依赖违规检测（tree-sitter）、基准编排。
- **语言前端（JVM，薄）**：Gradle / Maven 插件，只负责 APT 代码生成、构建期剪枝、JMH 实跑；以**子进程**被引擎调用，通过 JSON 交换数据。
- **契约**：两者间定义稳定的 JSON schema；将来加 Go / C# 前端时引擎不动。

### v1 的务实选择

若 v1 只支持 Java，分离架构属于**过度设计**。两个务实替代：

| 方案 | 做法 | 适用前提 |
|---|---|---|
| **V1-a（推荐）** | 全 Java 单体，用 **GraalVM Native Image**（或 jlink）打成自包含二进制，绕开 JDK 依赖 | 只想快速验证 Java 场景 |
| **V1-b** | 一开始就分离，引擎用 Go | 确定 v1 就要支持 Go，或极重视分发体验 |

GraalVM Native Image 的已知坑：反射需提供 `reflect-config.json`；Web 面板若用 Spring Boot 需改用 Quarkus / Micronaut 等原生友好框架。

## 1.4 连锁选型（问题 A 确定后）

| 能力 | 选型 | 自研还是复用 | 理由 |
|---|---|---|---|
| DI 切换 | Spring `@ConditionalOnProperty` / `@Primary`，或 Guice `bind().to()` | **复用** | MVP 只需生成绑定代码，绝不自造容器 |
| 微基准 | **JMH** | 复用，**硬要求** | 手写循环会被 JIT 死代码消除与预热差异彻底污染，不可省略 |
| 依赖违规检测 | **ArchUnit** | **复用** | 已能做「禁止依赖具体实现类」，且自带 `FreezingArchRule`；包一层即可，省掉 Phase 2 一大块工作量 |
| 编译期代码生成 | APT + 生成 **Java 源码文件**（非字节码） | 自研（薄层） | 生成源码可 diff、可 review、可人工确认，契合项目「人工审查」哲学；字节码织入不可读 |
| 运行时代理（过渡态） | ByteBuddy | 复用 | 仅接口变化时的临时方案 |
| 配置 | YAML（snakeyaml） | 复用 | — |

**关键建议：`§4.4 依赖违规检测` 不要自研，直接依赖 ArchUnit。** 这能把 Phase 2 的这一块从"数周"压到"数天"。

## 1.5 【关键修正】JVM 上「胶水开销」的真实来源

这是本次深挖最重要的发现，**它修正了 v1.0 的核心假设**。

v1.0 隐含假设是「接口 = 有开销，直接调用 = 无开销」。在 HotSpot 上**这个假设不成立**：

| 调用形态 | JIT 行为 | 真实开销 |
|---|---|---|
| 具体类直接调用 | 内联 | 基准 |
| **接口 + 构造注入，且 JVM 内只有 1 个实现类** | 接收者类型 profile 单态 → C2 **完全内联** | **≈ 0** |
| 接口 + 2 个实现类 | 双态内联缓存（TypeProfileWidth 默认 2） | 极小 |
| 接口 + ≥3 个实现类活跃（megamorphic） | 无法内联，itable 分派；接收者类型不精确还会拖累逃逸分析/标量替换 | 明显（ns 级，热点路径被放大） |
| `java.lang.reflect.Proxy` 动态代理 | 反射 + 装箱 + megamorphic | **大**（10–30ns/次起） |
| **每次调用都查容器**（`ctx.getBean(X.class)` 写在循环里） | Map 查找 + 可能反射 | **极大**（10–100ns/次），最常见的事故 |

**推论：胶水开销 ≠ 接口本身，而是这三个东西：**

1. **多态扇出** —— 同时活跃的实现数量（>2 即 megamorphic）
2. **查询位置** —— DI 查找发生在装配期（正确）还是每次调用（错误）
3. **中间层** —— 是否存在代理/适配/反射层

也就是说：**如果一个组件用构造注入、且同一时刻只有一个实现被加载，那么"未固化"状态下的开销就已经接近零，固化带来不了性能收益。**

这既是个坏消息也是个好消息：

- **坏消息**：v1.0 的性能叙事需要重写，「固化 = 性能优化」在最常见的场景下不成立。
- **好消息**：开销的机制被精确定义了，工具可以**精确地告诉用户胶水开销从哪来**，而且能在真正有开销的场景（megamorphic、代理层、逐次查容器）给出可量化的固化收益。这比"固化一定更快"诚实得多，也更有说服力。

## 1.6 Phase 0 基准实验的正确设计

基于 1.4，**原来的「接口 vs 直接调用」两组对照是错的设计**——它会测出 ≈0，然后让人误判项目没价值。应改为 **4 组**：

| 组 | 配置 | 预期 |
|---|---|---|
| **A** | 具体类直接调用 | 基准线 |
| **B** | 接口 + 构造注入，单实现 | ≈ A（验证「正确用法零开销」） |
| **C** | 接口 + 构造注入，3 个实现轮换调用 | 明显高于 A（量化 megamorphic 代价） |
| **D** | 动态代理 / 逐次查容器 | 远高于 A（量化错误用法代价） |

**固化收益 = C→B 或 D→B 的差值，而不是 A→B。**

要求：JMH，多轮预热，`-prof perfasm` 确认内联是否发生，**必须验证 B 组确实被内联**（否则实验无效）。

## 1.7 推论：固化 = 构建期剪枝

既然开销来自「多个实现同时被加载」，那么**消除开销最简单的方法不是代码生成，而是剪枝**：

> **固化时在构建产物中剔除未被选中的实现类（class 文件）。**

效果：调用点只剩一个实现类 → 必然单态 → JIT 必然内联 → 开销归零。

| 方案 | 成本 | 风险 | 可前移到 |
|---|---|---|---|
| **构建期剪枝**（删除未选中实现） | 极低（Gradle/Maven 的 shade/filter 配置） | 极低 | **Phase 1** |
| 生成源码替换接口调用 | 中（APT） | 中（改变调用方代码） | Phase 4 |
| 运行时代理 | 低 | 高（性能、语义） | 过渡态 |

**强烈建议把「构建期剪枝」从 Phase 4 提到 Phase 1。** 它几乎零成本，却能让 Phase 1 就兑现「固化后开销归零」的承诺——这解决了我在 v1.0 评审中指出的**顺序问题**（前三个阶段无法兑现核心卖点）。

补充手段：固化时把实现类标记为 `final`，进一步帮助 JIT 去虚拟化。

## 1.8 【新增】对外 API 组件 vs 内部实现组件

技术栈确定后暴露一个新问题：**固化若移除接口层，就是二进制不兼容变更（binary-incompatible breaking change）**。

如果组件被其他服务/团队通过 Maven 依赖，移除接口会直接破坏对方。必须分类：

| 类型 | 定义 | 固化允许的操作 |
|---|---|---|
| **内部实现组件** | 仅本模块内调用 | 允许完全移除胶水层（剪枝 + 代码重写 + `final`） |
| **对外 API 组件** | 被其他模块/服务通过接口依赖 | **只能锁定实现，禁止移除接口层** |

配置项：

```yaml
components:
  index:
    visibility: internal        # internal | public-api
    sealPolicy: full-strip      # internal 可用：full-strip | lock-only
```

`visibility: public-api` 的组件，密封操作强制降级为 `lock-only`，并在固化检查清单中显式提示。

## 1.10 【新增边界】胶水两侧的语言能否不同？

**结论：v1 明确不支持。这不是待办事项，而是与核心卖点互斥的设计选择——应当作为定位边界写进文档。**

### 两种「跨语言」性质完全不同

| 类型 | 例子 | 运行时 | 固化机制是否成立 |
|---|---|---|---|
| **I. 同运行时，不同源语言** | Java 调 Kotlin / Scala；C# 调 F# | 同一（字节码 / IL） | **成立**，虚分派性质相同 |
| **II. 跨运行时** | Java 调 Python；FFI；进程间 RPC | 不同 | **不成立** |

### 类型 II 为什么会让项目失去意义

1. **量级差 3–6 个数量级。** 单语言胶水开销是 **ns 级**（虚分派，约 3 ns）；跨运行时边界是 **μs 级**（序列化 / FFI / IPC，约 10 μs）。此时「胶水开销」不再是需要精细测量的百分比，而是压倒一切的主要成本——项目的量化叙事被它自己淹没。
2. **固化无法消除它。** 固化的机制是「移除间接层 → 单态 → JIT 内联 → 开销归零」。跨运行时的边界是**物理存在**的，不可能被内联掉。结果是：**sealed 状态下开销依然巨大，核心承诺直接失效。**
3. **差异化被 IDL 生态吃掉。** 跨语言时「接口」必须由 IDL 定义（Protobuf / Thrift / FlatBuffers / FFI header），而「从 IDL 生成多语言桩代码」是该生态的标准能力。§3.3 的「可塑型胶水」在跨语言场景下等价于一份手写的 IDL + 转换层，**没有增量价值**。
4. **成本是乘法。** 每增加一种语言对，就要一套映射规则 + 一套一致性测试 + 一套基准，而非线性叠加。
5. **问题域变了。** 两边语言不同时，「切换实现」往往等价于「换一个服务」，进入服务治理 / 服务网格的地盘——这正是 §8.1 自己排除掉的领域。

### 类型 I 可以做，但 v1 不做

技术上可行（同一字节码，可直接互调），固化机制完全适用。代价是静态分析要跨语言：

- Kotlin 生成的字节码带 `@Metadata`，可读但需额外解析；
- Scala 的隐式转换、Kotlin 的扩展函数会让「直接依赖具体实现类」的检测产生误判。

**列入 Phase 6+。** v1 没有必要为一个尚未验证的核心假设增加复杂度。

### 一个例外值得记录：GraalVM Polyglot

GraalVM 的 Truffle 框架**支持跨语言内联**（JS / Python / Ruby / LLVM bitcode 运行在同一运行时，Truffle AST 可跨语言优化）。这是唯一一种「固化后开销可能真的降下来」的跨语言路径。

但约束极多：必须跑在 GraalVM 上、语言必须有 Truffle 实现、性能特性与 HotSpot 完全不同（§1.5 那套分析要整个重做）。**有趣但太窄，不适合作为 v1 定位。**

### 由此确立的边界

> **胶水两侧必须同语言、同运行时。v1 为 Java → Java。**
> 若调用方与实现方语言不同，本工具不适用——请改用 IDL + codegen（Protobuf / Thrift）或服务治理方案。

**需要如实告知用户的一个边界**：如果真实需求是「把 Python 写的算法换成 Rust 实现」，这个工具帮不上忙。这不是缺陷，是定位。

# 二、深挖（四）：数据兼容性

## 2.1 五类耦合面

切换实现时，代码之外可能被打破的东西：

| # | 耦合面 | 例子 |
|---|---|---|
| 1 | **持久化格式** | 落盘索引的页格式、本地缓存快照、WAL、RocksDB SST |
| 2 | **序列化格式** | Java `Serializable`（`serialVersionUID`）、Kryo 注册 ID、Protobuf schema |
| 3 | **跨服务 wire format** | 组件输出被序列化后经 RPC/MQ/HTTP 传给别的服务 |
| 4 | **外部系统契约** | 数据库 schema、文件格式、对象存储布局 |
| 5 | **行为契约** | 迭代顺序、排序稳定性、哈希稳定性、并发语义、null/异常行为 |

## 2.2 最危险的是第 5 类（行为契约）

前四类至少会在解析时报错；**第 5 类会静默地给出错误结果**：

- **哈希函数改变** → 分布式分片全部错位 → 缓存雪崩
- **迭代顺序改变** → 分页结果错乱、限流窗口统计漂移
- **排序稳定性改变** → 同 key 记录顺序变化，对账不一致
- **异常类型改变** → 上层 catch 分支失效，错误处理静默降级

**致命点：这些在「集合相等」式的功能一致性测试里完全测不出来。** 必须专门断言顺序、稳定性和哈希。

## 2.3 设计补丁 A：为组件与实现声明「数据契约」

在 `swappable.yaml` 中新增 `dataContract` 段：

```yaml
components:
  index:
    interface: Index
    visibility: internal
    dataContract:
      persistence: none            # none | self-managed | external
      wireFormat: opaque           # opaque | schema:<ref>   （输出是否跨进程）
      behavioral:                  # 调用方依赖的行为契约，切换后必须仍成立
        - stable-iteration-order
        - null-hostile
        - no-concurrent-mutation
      schemaRef: null              # 跨进程时指向 protobuf/avro schema
    implementations:
      - name: bplus
        class: BPlusTreeIndex
        dataContract:
          formatId: index-bplus-v2
          compatibleWith: []       # 能直接读取的旧 formatId
          migrator: null
      - name: rbtree
        class: RedBlackTreeIndex
        dataContract:
          formatId: index-rbtree-v1
          compatibleWith: []
          migrator: IndexFormatMigrator   # 实现 Migrator 接口
```

### 切换时的自动兼容性判定

| 条件 | 判定 | 行为 |
|---|---|---|
| `formatId` 相同 | **直通** | 直接切换（现有模型） |
| 新实现的 `compatibleWith` 含旧 `formatId` | **直通（单向）** | 可切换，但**不可回滚** |
| 不同且配置了 `migrator` | **迁移** | 进入 migrating 状态 |
| 不同且无 migrator，但可从源头重建 | **重建** | 进入 rebuilding 状态 |
| 不同、无 migrator、且不可重建 | **阻断** | 拒绝切换，要求人工提供任一方案 |

## 2.4 设计补丁 B：扩展生命周期

v1.0 的状态机把「切换」当成原子操作，这是它最大的模型缺陷。含数据格式差异时不是。

```
                ┌──────────────────────────────────────┐
                ↓                                      │
 [创建] → experimental → candidate ──→ [preflight] ────┤
                                            │          │
                        ┌───────────────────┼──────────┐
                        ↓                   ↓          ↓
                  （直通：无数据差异）   rebuilding   migrating
                        │                   │          │
                        │              双写/追增量   双写 + 校验
                        │                   │          │
                        └─────→ verifying ←─┴──────────┘
                                    │
                          ┌─────────┴─────────┐
                          ↓                   ↓
                    sealed（固化）        rollback
                          │
                    unseal（解固化）
```

新增状态与职责：

| 状态 | 职责 | 退出条件 |
|---|---|---|
| `preflight` | 比对新旧 `dataContract`，判定切换类型，估算数据量与停机时间 | 输出切换方案，人工确认 |
| `rebuilding` | 后台建立新实现的数据，追增量（双写或 WAL 回放） | 新旧数据追平 |
| `migrating` | 运行 `Migrator`，双写，一致性校验 | 校验通过 |
| `verifying` | 校验和比对、抽样比对、count 一致性、影子读 | 全部通过 |
| `rollback` | 回退到旧实现 | — |

### 回滚的关键约束

**如果新实现已经写入了新格式数据，回滚需要反向迁移。**

因此规则：

1. `migrating` 状态要求 `Migrator` 实现**双向**（`forward` + `backward`），否则禁止进入；
2. 或要求迁移期**只追加不覆盖**，旧数据保留到 `sealed` 之后的一个观察期；
3. `rebuilding` 天然可回滚（旧数据未动），**应作为默认首选**。

## 2.5 三种切换模式

| 模式 | 适用 | 耗时 | 可回滚性 | 建议 |
|---|---|---|---|---|
| **直通 hot-swap** | 无持久化 / formatId 相同 | 秒级 | 完全 | 默认 |
| **重建 rebuild** | 数据可从源头重新生成 | 分钟–小时 | **强**（旧数据未动） | **优先于迁移** |
| **迁移 migrate** | 数据不可重建 | 小时+ | 弱（需反向迁移器） | 最后手段 |

**工具应强制优先「重建」而非「迁移」。** 只有当 `dataContract.persistence = self-managed` 且标注 `nonRebuildable: true` 时才允许进入 migrate。

## 2.6 核心架构建议：数据所有权外移

更根本的解法是**让数据问题不发生**：

> 未固化组件应只承担纯计算（in-memory 数据结构），**持久化与序列化由胶水层或上游负责**。

如此一来，切换实现永远是「直通 + 重建」，2.4 的复杂状态机只在存量组件上才需要。

这可以做成一条**可执行的检查项**，并入 §4.4 依赖违规检测：

```
[glue:data-ownership] 组件 `index` 的实现 `BPlusTreeIndex` 直接持有持久化逻辑
  → BPlusTreeIndex.java:142  (FileChannel.write)
  → BPlusTreeIndex.java:88   (serialize 私有实现)
  建议：将数据所有权外移到 IndexStore，使组件成为纯计算单元，
        切换实现即可降级为「重建」模式。
```

**这可能是「胶水」能给用户的最有价值的一条架构建议**——而且它是可自动检测的。

## 2.7 对 §4.3 测试体系的影响

功能一致性测试需新增以下用例类型：

| 用例类型 | 断言内容 |
|---|---|
| **顺序敏感断言** | 迭代顺序一致、排序稳定（同 key 相对次序不变） |
| **哈希稳定性** | 同一输入跨实现哈希值一致（当契约声明依赖分片时） |
| **序列化往返** | 实现 A 写 → 实现 B 读，须**明确成功或明确失败**，禁止静默出错 |
| **并发语义** | 相同并发操作序列下行为一致 |
| **边界行为** | null、空集合、超大数据、异常**类型**一致 |

尤其第三条：**最坏的结果不是迁移失败，而是迁移"成功"却读出了语义错误的数据。**

## 2.8 对 §4.5 风险等级的影响

数据耦合应成为风险等级的**最高权重因子**，取代"依赖模块数"。

| 权重 | 判定条件 |
|---|---|
| **最高** | `wireFormat: schema:*`（跨进程契约）或 `nonRebuildable: true` |
| **高** | `persistence: self-managed` |
| **中** | `persistence: external`，有直接实现类引用 |
| **低** | `persistence: none` 且 `wireFormat: opaque` |

依赖模块数保留为**次级**因子。

# 四、需要拍板的决策点

1. **技术栈确认（需分两问拍板）**：
   - **A 目标语言**：是否确为 JVM / Java？若目标是 Python / TS / JS / Rust，则「胶水开销」卖点不成立（§1.1），项目需重新定位。
   - **B 工具语言**：接受工具本身也用 Java（V1-a + GraalVM 打包），还是要求核心引擎用 Go 并采用分离架构（V1-b）？
2. **性能叙事怎么处理**：接受「多数正确用法下胶水开销已≈0，固化收益集中在 megamorphic / 代理层 / 逐次查容器三类场景」这一修正，还是坚持原叙事？
   - 选 A（诚实修正）：卖点变为「精确定位你的灵活性成本从哪来」，更有说服力但需重写 §7、§8。
   - 选 B（维持原叙事）：风险是用户实测后发现不符，信任受损。
3. **数据兼容性的范围**：v1 就支持 `rebuilding`/`migrating` 完整状态机，还是 v1 只做「检测 + 阻断」（发现数据不兼容就拒绝切换，给出人工指引）？
   - 建议选**只做检测+阻断**，成本低一个数量级，且已经能防住绝大多数事故。
